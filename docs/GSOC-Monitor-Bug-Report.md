# GSOC Monitor — Bug and Vulnerability Report

# Executive Summary

A structured review of the GSOC Monitor codebase found **50 confirmed defects** — 0 critical, 9 high, 19 medium and 22 low after independent verification. Every finding in this report was located in the current code by one reviewer and then re-examined by at least one adversarial reviewer whose instruction was to refute it; 4 candidate findings were rejected in that pass as documented, intentional design and are listed in the appendix so they are not re-raised.

**The headline.** The platform is in good shape for its age: no finding lets an anonymous caller read incident data, take over an account or execute code, and the crisis subsystem's per-entry sync paths hold up under scrutiny. The risk concentrates in four places:

1. **Session revocation does not exist.** Deleting a user does not end their session; a 30-day cookie keeps working against every authenticated route, including admin routes if they held that role (F-009). For a security-operations product this is the first thing to fix.
2. **Unauthenticated routes can be turned against the server.** The news endpoint fetches any URL a caller supplies (F-001); the crisis router parses 50 MB bodies before any authentication (F-005); the AI briefing route lets anyone drive paid model calls (F-003); the lightning query cache grows without bound on a public route (F-031); and the login rate limiter, keyed on the Heroku router's address, lets a stranger lock the whole team out of signing in (F-010).
3. **Concurrent operators can lose edits.** Whole-document last-write-wins, a debounce that clears before the write is in flight, and a reconnect that never resyncs mean two people working the same incident can silently overwrite each other (F-021, F-022, F-023) — exactly during the moments the workspace exists for.
4. **Some numbers on the screen are wrong.** Official AirNow monitors never render because the adapter is typed against the wrong schema (F-046); unknown containment shows as "0% contained" (F-048); the fire-potential strip is a day ahead every US evening (F-039); outage and hotspot counts truncate silently during exactly the large events that matter (F-047, F-050).

None of the fixes is architecturally hard. The remediation plan in this report groups them into an MVP gate (before customer exposure), a first hardening release, and a backlog.

## How to read this report

**Severity** follows the impact on a security-operations deployment. *Critical*: data loss, security breach or crash in a core flow. *High*: wrong operator-facing information or significant exposure. *Medium*: degraded behaviour under realistic conditions. *Low*: an edge case or a hardening gap. Where verification reviewers judged the original rating too high or too low, the calibrated rating is used and the change is noted on the card.

**IDs** are stable (`F-001` … `F-054`) and refer to the review's master list, which also contains the refuted candidates. Findings reported independently by more than one reviewer are marked as such; independent rediscovery is a strong signal.

**Verification.** Each card records how many adversarial reviews it survived, their confidence, and any correction the verifier made to the original claim. Where a verifier narrowed the scope of a finding, the narrowed version is what you should trust.

**Locations** are repository-relative paths with the line the reviewer anchored on; the defect is often a few lines either side.

## Authentication and sessions

The team's own login model: session lifetime, brute-force protection, account enumeration and the admin bootstrap.

<div class="finding"><div class="head"><span class="sev high">high</span><span class="id">F-009</span><span class="t">Deleted/offboarded users retain valid 30-day sessions — no revocation check anywhere</span></div>
<div class="loc">server/src/middleware/auth.ts:28 &middot; authentication</div>
<p><span class="k">What happens.</span> signToken() (server/src/middleware/auth.ts:24-26) issues a JWT valid for 30 days containing id/email/name/role, and requireAuth (lines 28-37) only does jwt.verify — it never checks that the user still exists or that the role claim is still current. requireAdmin (lines 39-47) trusts the token&#x27;s role claim. The admin &#x27;Delete a user&#x27; endpoint (server/src/routes/admin.ts:22-29) only removes the DB row; there is no token blacklist, no token versioning, and logout (server/src/routes/auth.ts:93-95) merely clears the cookie client-side. There is also no way to demote an admin (only delete), so the token role claim is the sole authority for 30 days.</p>
<p><span class="k">Failure scenario.</span> A GSOC operator is terminated and an admin deletes their account via DELETE /api/admin/users/:id. The ex-employee&#x27;s gsoc_auth cookie continues to pass requireAuth and requireAdmin for up to 30 more days: they can read every incident (/api/incidents), the team watchlist, publish/patch crisis share links, and — if they held role=admin — list all users&#x27; emails, delete other operators&#x27; accounts, and read/rotate the signup code (then re-register a fresh account with it). The only remediation is rotating JWT_SECRET, which logs out the entire team.</p>
<p><span class="k">Suggested fix.</span> On each authenticated request (or on a short cache), re-check the user row exists and read role from the DB (SELECT id, role FROM users WHERE id = $1); alternatively add a token_version column included in the JWT and bumped on delete/role change, or move to short-lived access tokens (~15 min) refreshed against the DB.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 2 independent reviews (confidence: high, high); severity calibrated from critical to high during verification. <span class="k">Reviewer note:</span> Severity calibrated to high rather than critical: exploitation requires a formerly legitimate account (no unauthenticated path), the exposure window is bounded at 30 days, and JWT_SECRET rotation is an available if disruptive kill switch. All cited lines and mechanisms are accurate as reported.</p></div>

<div class="finding"><div class="head"><span class="sev high">high</span><span class="id">F-010</span><span class="t">Login/signup brute-force limiter is keyed on req.ip with no &#x27;trust proxy&#x27; — on Heroku all users share the Heroku router&#x27;s IP, enabling a trivial team-wide login lockout</span></div>
<div class="loc">server/src/routes/auth.ts:15 &middot; authentication</div>
<p><span class="k">What happens.</span> The failure limiter (server/src/routes/auth.ts:12-26) and its checks (lines 36, 77) key on req.ip, but the app never calls app.set(&#x27;trust proxy&#x27;, ...) (no occurrence anywhere in server/src; Express default is false). Behind the Heroku router, req.ip is the router&#x27;s private connection address, not the client&#x27;s — so every client hitting the same router instance shares one failure bucket, and X-Forwarded-For is ignored. crisis.ts:190-192 has the same problem: share_access_log records router IPs, so the &#x27;COUNT(DISTINCT ip) viewers&#x27; stat (crisis.ts:199) reports router-fleet size, not real viewers.</p>
<p><span class="k">Failure scenario.</span> An anonymous attacker scripts bad logins until each Heroku router IP bucket accumulates 10 failures (a few hundred requests, no credentials). From then on tooManyFailures() returns true for every legitimate operator — the whole team gets 429 &#x27;Too many attempts&#x27; on /api/auth/login and /api/auth/signup for as long as the attacker keeps trickling requests, locking the GSOC out of its own dashboard during an incident. Conversely, per-attacker brute-force attribution is meaningless, and share-link &#x27;opened by N viewers&#x27; audit numbers shown to editors are wrong.</p>
<p><span class="k">Suggested fix.</span> Add app.set(&#x27;trust proxy&#x27;, 1) in server/src/index.ts (Heroku terminates exactly one proxy hop) so req.ip resolves from X-Forwarded-For; additionally add a per-account (email) failure counter so a distributed attack cannot be rate-limit-free and a single IP cannot lock out an account it doesn&#x27;t own.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 2 independent reviews (confidence: high, high). <span class="k">Reviewer note:</span> The lockout does not evict logged-in operators: existing 30-day gsoc_auth JWT cookies keep working (middleware/auth.ts:28-37 never checks the failure map). Only new logins and signups are blocked.</p></div>

<div class="finding"><div class="head"><span class="sev low">low</span><span class="id">F-015</span><span class="t">Login timing oracle enumerates registered emails (bcrypt runs only when the account exists)</span></div>
<div class="loc">server/src/routes/auth.ts:84 &middot; authentication</div>
<p><span class="k">What happens.</span> In POST /api/auth/login, &#x27;if (!user || !(await bcrypt.compare(password, user.password_hash)))&#x27; short-circuits: an unknown email answers in milliseconds, while a known email spends a full bcryptjs cost-12 compare (~1s of CPU per the file&#x27;s own comment at auth.ts:9-10) before the identical 401 body. The response text is uniform but the latency difference is roughly two orders of magnitude — trivially measurable remotely.</p>
<p><span class="k">Failure scenario.</span> An attacker who cannot pass the signup-code gate replays /api/auth/login with a junk password across a list of corporate email addresses (within the 10-failure budget per window, or slowly over time) and classifies each address by response time, building an accurate roster of GSOC operator accounts to target with password spraying and phishing.</p>
<p><span class="k">Suggested fix.</span> When no user row is found, run bcrypt.compare against a precomputed dummy hash so both paths cost the same, keeping the shared 401 response.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 1 independent review (confidence: high). <span class="k">Reviewer note:</span> Note that index.ts never sets `trust proxy`, so on Heroku `req.ip` is the router&#x27;s address rather than the client&#x27;s — the 10-per-window budget the finding cites is per-router bucket, not per-attacker, which if anything makes slow enumeration easier (and is a separate issue).</p></div>

<div class="finding"><div class="head"><span class="sev low">low</span><span class="id">F-016</span><span class="t">Signup code generated with Math.random() instead of a CSPRNG</span></div>
<div class="loc">server/src/routes/admin.ts:10 &middot; security</div>
<p><span class="k">What happens.</span> randomCode() in server/src/routes/admin.ts:8-11 and its duplicate in server/src/migrate.ts:4-7 build the 8-character signup code — the only credential gating account creation — from Math.random(), a non-cryptographic PRNG whose V8 xorshift128+ state is recoverable from observed outputs. The codebase itself uses the correct primitive elsewhere: crisis.ts:27-29 generates share passwords with crypto.randomInt.</p>
<p><span class="k">Failure scenario.</span> Any context where Math.random outputs from the same process become observable (another endpoint or dependency exposing values derived from the shared PRNG stream, or a future code path added under the same assumption) lets an attacker reconstruct the generator state and predict the current or next rotated signup code, then self-register an account on the security dashboard. Even absent that, 8 chars of a 32-symbol alphabet is the sole gate to enrollment, and the rate limiter guarding it is broken on Heroku (see the trust-proxy finding).</p>
<p><span class="k">Suggested fix.</span> Use crypto.randomInt(ALPHA.length) in both randomCode() implementations (mirroring crisis.ts:28), and deduplicate the two copies.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 1 independent review (confidence: high).</p></div>

<div class="finding"><div class="head"><span class="sev low">low</span><span class="id">F-017</span><span class="t">First-user-becomes-admin check races: concurrent signups on an empty users table can both receive the admin role</span></div>
<div class="loc">server/src/routes/auth.ts:51 &middot; concurrency</div>
<p><span class="k">What happens.</span> POST /api/auth/signup runs &#x27;SELECT COUNT(*) FROM users&#x27; (server/src/routes/auth.ts:51-54) and then a separate INSERT (lines 57-62) with no transaction, lock, or serialization. Two requests interleaving both read count=0 and both insert with role=&#x27;admin&#x27;.</p>
<p><span class="k">Failure scenario.</span> During initial rollout the signup code is shared with the team and two operators submit the form within the same ~1s window (each request also spends ~1s in bcrypt.hash between the count and the insert, widening the race). Both accounts are created as admin; the unintended admin can delete users, read/rotate the signup code, and manage the IAP library, and nothing in the UI flags it — there is no role display/demotion tooling, only user deletion.</p>
<p><span class="k">Suggested fix.</span> Make the first-admin promotion atomic, e.g. INSERT ... role = CASE WHEN NOT EXISTS (SELECT 1 FROM users) THEN &#x27;admin&#x27; ELSE &#x27;member&#x27; END inside a single statement, or take a transaction with LOCK TABLE users / an advisory lock around count+insert.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 1 independent review (confidence: medium). <span class="k">Reviewer note:</span> bcrypt.hash (auth.ts:48) executes before the COUNT (auth.ts:51), not between the count and the insert; the race window is only the COUNT-&gt;INSERT gap (one DB round trip), so the &#x27;~1s&#x27; widening claim is wrong and the practical trigger window is milliseconds.</p></div>

## Share links and incident data exposure

The public door into crisis data. Share links are the one path that reaches outside the team, so every weakness here is a disclosure risk.

<div class="finding"><div class="head"><span class="sev medium">medium</span><span class="id">F-011</span><span class="t">Public /api/intel feed discloses the team&#x27;s OSINT watchlist source labels (and failing-source labels) to anyone, cross-origin</span></div>
<div class="loc">server/src/routes/intel.ts:9 &middot; data-handling</div>
<p><span class="k">What happens.</span> GET /api/intel has no auth (server/src/routes/intel.ts:7-11). getIntel() (server/src/intel/service.ts:281-291) returns every buffered item including its `source` field — the human-entered label of the watchlist row (intel/types.ts:61) — plus `errors`, the labels of sources that failed this cycle (types.ts:78). Team-added rows are loaded from watchlist_sources (service.ts:142-150), whose CRUD is deliberately auth-gated (server/src/routes/watchlist.ts:12), but their labels and item streams leak straight through this unauthenticated endpoint. app.use(cors()) (index.ts:92) additionally serves Access-Control-Allow-Origin: * so any web page can read it silently.</p>
<p><span class="k">Failure scenario.</span> An adversary (or any curious visitor) GETs https://&lt;app&gt;.herokuapp.com/api/intel with no account and reads the team-configured source labels — e.g. a Bluesky search on an executive&#x27;s name, a scanner agency covering a specific facility, a Socrata crime dataset for a site&#x27;s city — revealing exactly what assets, people, and locations the security team is monitoring, and (via `errors`) which collection is currently blind. The individual items are public OSINT, but the collection plan is not.</p>
<p><span class="k">Suggested fix.</span> Put requireAuth on /api/intel (the client is already an authenticated SPA), or strip team-added source labels/errors from the unauthenticated response and expose them only to signed-in users.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 1 independent review (confidence: high).</p></div>

<div class="finding"><div class="head"><span class="sev medium">medium</span><span class="id">F-012</span><span class="t">Crisis share view key is a replayable bearer credential carried in the query string of every viewer request, so it accumulates in router/proxy logs</span></div>
<div class="loc">server/src/routes/crisis.ts:41 &middot; data-handling</div>
<p><span class="k">What happens.</span> viewKeyOk reads the credential from req.query.k (server/src/routes/crisis.ts:39-47), and the client appends ?k=&lt;sha256(password)&gt; to every share request — snapshot fetches, checklist toggles, the IAP PDF and the SSE stream (client/src/crisis/CrisisShareView.tsx:377, 413, 421, 436, 484, 578). The wire key is the actual credential (the server stores sha256 of it), it never expires while the link lives, and Heroku router logs record the full request path including the query string, as do corporate proxies in front of external stakeholders&#x27; browsers.</p>
<p><span class="k">Failure scenario.</span> Token+k pairs for a live incident land in the Heroku log stream and any attached log drain (Papertrail etc.). Anyone with read access to those logs — a logging add-on breach, a contractor with log access, a stakeholder-side proxy admin — replays GET /api/crisis/share/&lt;token&gt;?k=&lt;key&gt; to read the live situation report for a security incident and can POST checklist toggles (crisis.ts:293-326), corrupting the ICS checklist state, all without ever having been given the link or password.</p>
<p><span class="k">Suggested fix.</span> Send the key in a header or request body for fetch/POST paths, and for the EventSource path exchange the key once (POST) for a short-lived, HttpOnly, path-scoped cookie or a short-TTL signed query token; at minimum note that log drains must be treated as credential stores.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 2 independent reviews (confidence: high, high); reported independently by 2 reviewers; severity calibrated from high to medium during verification. <span class="k">Reviewer note:</span> The alt-title claim is also accurate: crisis.ts:46 `|| hashEquals(key, passwordHash)` accepts the stored password_hash itself as a valid ?k=, kept for &#x27;interim deployment&#x27; rows (43-45), which contradicts the comment at 20-22 that a DB read yields nothing replayable.</p></div>

<div class="finding"><div class="head"><span class="sev low">low</span><span class="id">F-018</span><span class="t">Plaintext share-link password is stored in the incident JSONB blob and returned to every authenticated user (and any incidents-table dump)</span></div>
<div class="loc">client/src/crisis/crisisStore.ts:678 &middot; data-exposure</div>
<p><span class="k">What happens.</span> addShareLink() writes the server-generated plaintext `password` into incident.shareLinks[].password. IncidentSync.pushIncident (IncidentSync.tsx:41) sends the whole incident on POST/PUT WITHOUT stripping shareLinks (only actionLog/checklists are cleared), so incidents.ts stores shareLinks[].password verbatim in incidents.data. GET /api/incidents (incidents.ts:45-50) returns the entire data blob to any authenticated user with no role filter. share_links deliberately stores only a double-SHA hash, but the sibling incidents table holds the plaintext, so a dump of incidents — or any account holder, including a low-privilege &#x27;viewer&#x27; role — recovers every share link&#x27;s plaintext password and can derive the exact ?k= to open the gated link. This is the at-rest exposure the crisis.ts header (lines 20-24) claims does not exist, reintroduced through a different table.</p>
<p><span class="k">Failure scenario.</span> A &#x27;viewer&#x27;-role account (or an attacker with a stale incidents backup) calls GET /api/incidents. The JSON response includes incidents[*].shareLinks[*].password in plaintext for every link ever published. The attacker copies a password, opens /?share=&lt;token&gt;, types it, and reads a report they were never given the link&#x27;s password for. extractPublicState correctly omits shareLinks, so the leak is not via the share view — it is via the authenticated incidents API and DB at rest.</p>
<p><span class="k">Suggested fix.</span> Do not persist the plaintext password in the synced incident blob. Strip shareLinks[].password before the PUT/POST body (as actionLog/checklists are stripped), or hold the plaintext only in ephemeral client state / a separate auth-gated endpoint keyed to the token; never write it into incidents.data.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 2 independent reviews (confidence: high, high); severity calibrated from high to low during verification. <span class="k">Reviewer note:</span> There is no &#x27;viewer&#x27; role: auth.ts:54 assigns &#x27;admin&#x27; to the first registrant and &#x27;member&#x27; to everyone else, and admin.ts has no role-change endpoint. Every member already has unfiltered read/write on all incidents and can mint their own share links via POST /api/crisis/publish, so an in-team password read grants nothing beyond what they already hold — the crisis.ts comment treats this as accepted &#x27;auth-only&#x27; data. The real residual defect is the at-rest one: a DB dump/backup already contains share_links.snapshot (the same public state) plus share_links.token, so recovering shareLinks[].password from incidents.data only adds unauthenticated live viewing of the public subset for the remaining &lt;=72h TTL (crisis.ts:76-77, renewable only with auth). It defeats the documented double-hash control but with modest practical impact; &#x27;high&#x27; is overstated.</p></div>

<div class="finding"><div class="head"><span class="sev low">low</span><span class="id">F-020</span><span class="t">Incident deletion revokes share links best-effort with a swallowed error, and the claimed DB cascade does not exist</span></div>
<div class="loc">server/src/routes/incidents.ts:255 &middot; access-control</div>
<p><span class="k">What happens.</span> DELETE /api/incidents/:id deletes the incident row first (line 251) and only then calls revokeShareLinksForIncident(...).catch(() =&gt; 0) (line 255), swallowing any error. The share_links schema (migrate.ts:44-50) declares incident_id as a plain TEXT column with NO foreign key, despite the comment on line 43 claiming &#x27;deleting an incident cascades&#x27; — so the database performs no cascade. If the revocation query throws (transient DB error, connection drop, or the process dies between the DELETE and the revoke), the share_links rows remain active=TRUE and unexpired, and continue serving the deleted incident&#x27;s last snapshot (personnel names, full action log, property watch) until each link&#x27;s own publish+72h expiry — with no incident record left to re-revoke them from.</p>
<p><span class="k">Failure scenario.</span> An operator deletes an active incident. A pool hiccup makes the follow-up revoke query throw; the .catch returns 0 and the API responds { ok:true, revokedShareLinks:0 }. The incident is gone from the workspace, but its share links keep answering GET /api/crisis/share/&lt;token&gt; with the full frozen snapshot for up to 72h, and no UI surfaces them because the incident no longer exists.</p>
<p><span class="k">Suggested fix.</span> Do the delete and revoke in one transaction (revoke first, or add ON DELETE handling that flips active), and add the real FK or a DB-side trigger so links cannot outlive their incident even if the app path fails; surface a non-zero failure to the caller instead of swallowing it.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 1 independent review (confidence: medium); severity calibrated from medium to low during verification. <span class="k">Reviewer note:</span> Orphaned links are not entirely unrecoverable: DELETE /api/crisis/share/:token (crisis.ts:247) still works for any authenticated user who has the token (e.g. from the shared URL); only the incident-side UI affordance is lost. Exposure is also bounded by the 72h expires_at every live row carries, including legacy links backfilled by migrate.ts:174-177.</p></div>

<div class="finding"><div class="head"><span class="sev low">low</span><span class="id">F-025</span><span class="t">share_links snapshot updates are unlocked read-modify-write: auto-publish PATCH and checklist fan-out race and the loser&#x27;s fields vanish from the public snapshot</span></div>
<div class="loc">server/src/routes/crisis.ts:150 &middot; concurrency</div>
<p><span class="k">What happens.</span> PATCH /api/crisis/share/:token does `SELECT snapshot` (lines 138-141), merges in JS keeping `prevChecklists` from ITS OWN read (lines 149-155), then `UPDATE share_links SET snapshot = $1` (lines 158-161) — no transaction, no row lock, no version. `updateShareChecklists` (lines 271-288) is the same pattern per link: `SELECT token, snapshot` then `UPDATE ... SET snapshot = $1` with the checklist map captured inside the caller&#x27;s already-committed toggle transaction. It is invoked concurrently from crisis.ts:321 and incidents.ts:119 for every toggle, while the editor&#x27;s auto-publish PATCH fires 1.5 s after ANY incident change (IncidentSync.tsx:120-134). Two interleavings lose data: (a) PATCH reads S0 (checklists C0) → toggle fan-out writes S0+C1 → PATCH writes {S0, body, checklists: C0}: the viewer&#x27;s toggle is erased from the snapshot, and stays erased because every later PATCH re-preserves the snapshot&#x27;s own map; (b) two toggles ~10 ms apart commit C1={a} then C2={a,b} under the incidents row lock, but their fan-outs are unordered — if fan-out 1&#x27;s UPDATE lands after fan-out 2&#x27;s, the snapshot ends with {a} only. Viewers receive the SSE `update` events in the same wrong order and render the regressed map (CrisisShareView.tsx:415 does a plain `setData`).</p>
<p><span class="k">Failure scenario.</span> Property staff viewer checks &#x27;Account for all guests&#x27; on the share page while the editor is typing the executive summary. The toggle commits to the incidents row and its fan-out starts; the editor&#x27;s auto-publish PATCH (armed by the typing) reads the snapshot in the same few-millisecond window and writes back the map it read (unchecked). The share page briefly shows the item checked, then receives the PATCH&#x27;s `update` event with it unchecked; every subsequent auto-publish preserves the unchecked map, and the editor&#x27;s checklist tab (fed from the incidents row) shows it checked — the two audiences disagree until someone toggles that item again.</p>
<p><span class="k">Suggested fix.</span> Make both writes single atomic SQL statements instead of JS merges: PATCH → `UPDATE share_links SET snapshot = (snapshot || $1::jsonb) || jsonb_build_object(&#x27;checklists&#x27;, COALESCE(snapshot-&gt;&#x27;checklists&#x27;, $1::jsonb-&gt;&#x27;checklists&#x27;), &#x27;lastUpdated&#x27;, $2) WHERE token=$3 AND &lt;LIVE&gt; RETURNING snapshot`; fan-out → `UPDATE share_links SET snapshot = jsonb_set(snapshot, &#x27;{checklists}&#x27;, $1::jsonb) WHERE incident_id=$2 AND &lt;LIVE&gt; RETURNING token, snapshot`, and broadcast the RETURNING value. Alternatively wrap SELECT ... FOR UPDATE + UPDATE in a transaction.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 1 independent review (confidence: high); severity calibrated from medium to low during verification.</p></div>

## Public routes: request forgery, abuse and cost exposure

Every data route is unauthenticated by design. These findings are the places where an anonymous caller can make the server fetch, buffer, spend or hammer on their behalf.

<div class="finding"><div class="head"><span class="sev high">high</span><span class="id">F-001</span><span class="t">Unauthenticated GET /api/news?extra= makes the server fetch arbitrary attacker-supplied URLs (SSRF / open fetch proxy) with no host, scheme, count or redirect checks</span></div>
<div class="loc">server/src/routes/news.ts:226 &middot; security</div>
<p><span class="k">What happens.</span> news.ts:224-231 JSON.parses the public `?extra=` query param into an array of {url,label} and news.ts:255-261 runs `fetchFeed(f.url, ...)` for EVERY entry via Promise.allSettled. fetchFeed (news.ts:159-165) calls `fetch(url)` with the server&#x27;s identity and follows redirects; the only guard is the try/catch around JSON.parse. There is no auth (index.ts:132 mounts newsRouter with none), no scheme/host validation (contrast the watchlist route&#x27;s isSafeHttpUrl and adapters.ts:21 post-redirect re-check, which this path lacks), no cap on the number of URLs, and the per-URL cache key `news:extra:${f.url}` (line 257) lets each distinct URL occupy one of the 2000 shared cache slots (cache.ts:16).</p>
<p><span class="k">Failure scenario.</span> Anonymous request `GET /api/news?extra=[{&quot;url&quot;:&quot;http://10.0.0.5:8080/internal.rss&quot;,&quot;label&quot;:&quot;x&quot;}]` (or a public URL that 302s to http://127.0.0.1:&lt;PORT&gt;/…) makes the dyno issue the GET from inside the platform network; any RSS-shaped response has its &lt;title&gt;/&lt;link&gt;/&lt;media:*&gt; values returned to the caller as news items (blind for other content, with an 8s-timeout timing oracle for host/port discovery). A single request carrying ~500 URLs fans out into ~500 concurrent outbound fetches with unbounded response buffering (`r.text()`), so a few requests per second turn the server into a DDoS/amplification relay and can exhaust dyno memory; 2000 distinct URLs also evict every other layer&#x27;s cached upstream result (aqi, fire-outlook, smoke, radar…), forcing rate-limited re-fetches.</p>
<p><span class="k">Suggested fix.</span> Require auth for extra feeds (or move custom feeds to the authenticated watchlist path); validate each URL with the same isSafeHttpUrl/public-host logic as watchlist.ts, resolve and reject private/loopback/link-local IPs, re-validate `r.url` after redirects, cap extras per request (e.g. 5) and cap response size; key the cache by a hash and a separate small namespace so extras cannot evict core entries.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 1 independent review (confidence: high). <span class="k">Reviewer note:</span> On Heroku&#x27;s common runtime the reachable internal surface is limited (loopback to the app itself; instance metadata is not routable), so the &#x27;internal network&#x27; half of the scenario is weaker than in a VPC deployment; the open-relay/fan-out, unbounded response buffering and cache-eviction DoS vectors are fully demonstrable as written.</p></div>

<div class="finding"><div class="head"><span class="sev high">high</span><span class="id">F-005</span><span class="t">50 MB JSON body limit applies to unauthenticated /api/crisis routes, letting anyone force the single dyno to buffer and parse 50 MB per request</span></div>
<div class="loc">server/src/index.ts:98 &middot; security</div>
<p><span class="k">What happens.</span> index.ts:98 registers `express.json({ limit: &#x27;50mb&#x27; })` for the whole /api/crisis prefix. That prefix includes public, token-only routes with no requireAuth: POST /share/:token/checklist/:itemId (crisis.ts:293) and the GET routes. Body parsing runs before the handler, so the 50 MB buffer + synchronous JSON.parse happen before invalidToggleReason (checklist.ts:31) rejects the body or before the token is even looked up. The comment on lines 94-97 acknowledges the 1 MB default exists precisely to stop this, but exempts this public surface.</p>
<p><span class="k">Failure scenario.</span> An anonymous client sends 20 parallel `POST /api/crisis/share/x/checklist/a` requests each with a 50 MB JSON body of nested arrays. The dyno holds up to ~1 GB of raw bodies, then JSON.parse blocks the event loop for hundreds of ms per body; Heroku R14/R15 memory errors or a restart follow, taking down every layer and live share page. Only editors ever need the large limit for /publish and PATCH /share/:token.</p>
<p><span class="k">Suggested fix.</span> Register the 50 MB parser only on the two authenticated write routes (after requireAuth, e.g. `router.post(&#x27;/publish&#x27;, requireAuth, express.json({limit:&#x27;50mb&#x27;}), …)`) and leave the public checklist route on the 1 MB default (its body is a boolean + short string).</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 2 independent reviews (confidence: high, high); reported independently by 3 reviewers. <span class="k">Reviewer note:</span> Two details make the exposure broader than stated: (1) the parser is prefix-mounted, so any POST/PUT/PATCH to any path under /api/crisis (even a nonexistent one, or DELETE/GET with a body) triggers the 50 MB buffer + parse, not only the checklist route; (2) body-parser 1.20.5 (locked in package-lock.json) defaults to `inflate: true` and raw-body enforces the limit on the decompressed stream, so an attacker can upload a ~50 KB gzip/deflate body with `Content-Encoding` and still force ~50 MB of buffering per request, so the attack needs negligible bandwidth.</p></div>

<div class="finding"><div class="head"><span class="sev medium">medium</span><span class="id">F-002</span><span class="t">Watchlist SSRF guard is hostname-shaped only: DNS names resolving to private/loopback IPs and arbitrary ports pass validation and are fetched by the ingest engine</span></div>
<div class="loc">server/src/routes/watchlist.ts:26 &middot; security</div>
<p><span class="k">What happens.</span> watchlist.ts:26-44 (`HOSTNAME_RE`, `IPV4_RE`, `isPublicHostname`, `isSafeHttpUrl`) and the defense-in-depth copy in adapters.ts:125-139 only check that the hostname is a dotted DNS name with an alphabetic TLD and is not a dotted-quad. Nothing resolves the name or checks the resulting address, and although the comment on line 22 says &#x27;no port&#x27;, `u.hostname` excludes the port so any `:port` is accepted. adapters.ts:21 re-checks `r.url` after redirects with the same hostname-only test, so redirects to such names also pass. Every active row is then fetched every 90s by the background cycle (service.ts:207-212, adapters.ts:12-23).</p>
<p><span class="k">Failure scenario.</span> Any signed-in member POSTs /api/watchlist {kind:&#x27;rss&#x27;, label:&#x27;x&#x27;, url:&#x27;http://127.0.0.1.nip.io:5174/api/admin/users&#x27;} (or 169.254.169.254.nip.io, or a domain they control whose A record is 10.x/127.x). Validation passes (labels are alphanumeric, TLD &#x27;io&#x27;, not a dotted-quad), the row is saved, and from then on the server GETs that internal target from its own network every 90 seconds, indefinitely, with RSS-shaped responses parsed into the public /api/intel feed.</p>
<p><span class="k">Suggested fix.</span> In both validators resolve the hostname (dns.lookup, all addresses) and reject loopback, RFC1918, link-local, CGNAT, ULA and multicast ranges; reject non-default ports (or allowlist 80/443); apply the same check to the post-redirect `r.url` in adapters.fetchText.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 1 independent review (confidence: high); reported independently by 2 reviewers. <span class="k">Reviewer note:</span> Additional mechanism detail: the post-redirect re-check at adapters.ts:21 runs after `await fetch(...)` has already followed the redirect and completed the request to the final host — it only discards the body. So even a redirect to a dotted-quad private IP (which the regex would reject) still causes the GET to be issued; only the response is dropped.</p></div>

<div class="finding"><div class="head"><span class="sev medium">medium</span><span class="id">F-003</span><span class="t">POST /api/briefing is unauthenticated: anyone can drive paid Anthropic calls with arbitrary 30 KB payloads and no rate limit</span></div>
<div class="loc">server/src/routes/briefing.ts:144 &middot; security</div>
<p><span class="k">What happens.</span> index.ts:148 mounts briefingRouter without requireAuth and briefing.ts:144-190 has no auth or rate limiting. The only checks are isSignals (an object with ≤40 groups and a recentEvents array, line 138-142) and a 30,000-char cap (line 151). When ANTHROPIC_API_KEY is set, each request whose payload hash misses the 20-entry cache (line 55-56, 161-166) calls `client.messages.create` with the attacker&#x27;s full payload as the user message (line 112-119).</p>
<p><span class="k">Failure scenario.</span> An anonymous script POSTs /api/briefing with `{signals:{groups:[],recentEvents:[&lt;30 KB of random text&gt;]}}` in a loop, varying one character per request so every call misses the payload-hash cache; each call costs ~8k input tokens against the operator&#x27;s API key, with no ceiling, until the key&#x27;s spend limit is hit or the account is exhausted — after which real operators&#x27; briefings silently degrade to the rules fallback (line 172-177).</p>
<p><span class="k">Suggested fix.</span> Apply requireAuth to the router (the panel is only shown to signed-in operators), add a per-user/IP token bucket, and cap MAX_PAYLOAD_CHARS tighter or ignore recentEvents beyond a fixed count.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 1 independent review (confidence: high).</p></div>

<div class="finding"><div class="head"><span class="sev medium">medium</span><span class="id">F-006</span><span class="t">/api/news-map forwards unbounded arbitrary ?query= strings to GDELT per distinct value and /debug bypasses the cache entirely, letting any client exhaust GDELT&#x27;s 1-req/5s limit</span></div>
<div class="loc">server/src/routes/newsMap.ts:231 &middot; security</div>

## Multi-operator sync and data loss

The crisis workspace synchronises several operators through a debounced last-write-wins blob plus per-entry paths for the log and checklists. These are the windows in which an edit can be silently lost, resurrected or shown as saved when it is not.

<div class="finding"><div class="head"><span class="sev high">high</span><span class="id">F-021</span><span class="t">Incident blob PUT is unconditional last-write-wins: two operators editing different fields of the same incident silently erase each other&#x27;s changes</span></div>
<div class="loc">server/src/routes/incidents.ts:88 &middot; concurrency</div>
<p><span class="k">What happens.</span> PUT /api/incidents/:id (incidents.ts:88-96) replaces the whole `data` JSONB with the client&#x27;s blob (`data = $1::jsonb || jsonb_build_object(...)`), preserving only `actionLog` and `checklists`; the WHERE clause is `id = $2` alone — there is no version/updated_at predicate, and the incidents table has no version column (server/src/migrate.ts:35-40). Every other field (roles, assignments, personnel, drawLayers, executiveSummary, intake, shareLinks, aar, status...) rides this blob. On the client, IncidentSync.tsx:75-84 debounces the PUT 1.5 s and re-arms the timer on every keystroke (line 77), and the SSE upsert handler drops every peer change while that timer is armed (`if (pending.has(inc.id)) return;`, line 218). So while operator A types anywhere in the incident, A&#x27;s client is blind to peers, and A&#x27;s eventual PUT carries A&#x27;s stale copy of every field B touched. The server has no way to detect that A&#x27;s write is based on an older version. The same missing check also lets two PUTs from the SAME client land out of order (a slow first PUT overtaken by the second): the older body is applied last, and because the client&#x27;s `serverState` holds the newer canon (line 34) the older echo differs and is applied at line 245-247, reverting the operator&#x27;s own newer edit locally too.</p>
<p><span class="k">Failure scenario.</span> Operator A is typing in the executive summary (pending timer continuously re-armed). Operator B assigns &#x27;Jane Doe&#x27; as Operations Section Chief; B&#x27;s PUT commits and the server broadcasts. A&#x27;s client discards the broadcast at IncidentSync.tsx:218. 1.5 s after A&#x27;s last keystroke, A&#x27;s PUT sends A&#x27;s blob whose `assignments` array lacks Jane → server overwrites `data` → the assignment is gone from the DB; B&#x27;s client receives A&#x27;s echo (blobSame false) and `applyRemoteUpsert` (crisisStore.ts:998-1007) removes Jane from B&#x27;s org chart as well. The system log entry &#x27;Jane Doe assigned as Operations Section Chief&#x27; survives (log path is append-only), so the record now says she was assigned while the ICS chart shows the seat empty. Same outcome for draw layers, personnel, roles, intake answers, status and AAR text edited concurrently.</p>
<p><span class="k">Suggested fix.</span> Add an integer `version` column to incidents; have the client send the version it based its edit on and the server execute `UPDATE ... WHERE id=$2 AND version=$3 RETURNING data, version` (409 on zero rows, client then rebases its field-level patch onto the returned row and retries). Longer term, replace the whole-blob PUT with per-field PATCHes so unrelated fields never collide, the same way the log and checklists already do.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 2 independent reviews (confidence: high, high); severity calibrated from critical to high during verification. <span class="k">Reviewer note:</span> Severity: the mechanism and scenario are accurate, but this is a concurrency data-loss bug requiring two operators to edit the same incident at overlapping times, with no security or availability impact and the lost edits re-enterable; &#x27;high&#x27; is the better calibration than &#x27;critical&#x27;. Note the auto-publish path (IncidentSync.tsx:107-137) means a stale blob is also pushed to live share links, so viewers see the regression too.</p></div>

<div class="finding"><div class="head"><span class="sev high">high</span><span class="id">F-022</span><span class="t">Debounce entry is removed before the PUT is sent, so a peer broadcast arriving during the request&#x27;s flight overwrites the operator&#x27;s unsaved edit in the store</span></div>
<div class="loc">client/src/crisis/IncidentSync.tsx:80 &middot; concurrency</div>
<p><span class="k">What happens.</span> scheduleSync&#x27;s timer callback does `pending.delete(incident.id)` (line 80) and only then calls `pushIncident` (line 81), which sets `serverState` to the optimistic canon (line 34) and starts the fetch. For the entire network round-trip of the PUT there is no entry in `pending`, so the SSE `upsert` handler&#x27;s only guard (`if (pending.has(inc.id)) return;`, line 218) does not fire. Any broadcast for this incident during that window — and the server broadcasts the FULL incident row on every peer log append/edit/delete (incidents.ts:170), every checklist toggle (incidents.ts:118, crisis.ts:319) and every peer PUT — carries the pre-PUT blob. Its canon differs from the optimistic baseline, so lines 240-247 call `applyRemoteUpsert`, which replaces the whole incident in the store (crisisStore.ts:1004) with the server&#x27;s OLD blob, and `serverState` is reset to that old canon (line 245). The operator&#x27;s just-typed text disappears from the controlled inputs until (and only if) the PUT&#x27;s own echo arrives later.</p>
<p><span class="k">Failure scenario.</span> Operator A finishes typing &#x27;Evacuating deck 4 via aft stairs&#x27; in the executive summary; 1.5 s later the PUT goes out (~150-400 ms on Heroku). During that window operator B saves a log entry; the server&#x27;s broadcast of the incident row (still containing the old summary) reaches A. A&#x27;s client applies it: the textarea snaps back to the old summary. A, mid-sentence, types the next character — the controlled textarea&#x27;s onChange now emits OLD_TEXT + char, `update()` stores it, the watcher schedules a PUT, and 1.5 s later the server (which by now holds &#x27;Evacuating deck 4 via aft stairs&#x27;) is overwritten with the old text → the sentence is permanently lost. If instead A&#x27;s PUT echo is lost (SSE reconnect, finding 3), the reversion is permanent in A&#x27;s UI even without typing, and A&#x27;s next edit of any field overwrites the server with the stale blob.</p>
<p><span class="k">Suggested fix.</span> Track in-flight incidents separately (add to an `inflight` set in pushIncident, remove in .then/.catch) and make the upsert handler skip — or field-merge — while `pending.has(id) || inflight.has(id)`; after the PUT settles, re-diff the store against the response and schedule a follow-up PUT if they differ. Combined with the version check from finding 1, a stale peer broadcast can also be rejected by version.</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 1 independent review (confidence: high).</p></div>

<div class="finding"><div class="head"><span class="sev high">high</span><span class="id">F-023</span><span class="t">Editor SSE stream never resyncs after a reconnect: changes made during the gap are lost from the client&#x27;s view and its stale baselines later overwrite peers</span></div>
<div class="loc">client/src/crisis/IncidentSync.tsx:260 &middot; concurrency</div>
<p><span class="k">What happens.</span> The editor live-sync relies entirely on the EventSource at line 210. The initial GET /api/incidents runs exactly once per login (`loaded.current` guard, lines 148-149). On a dropped stream the browser reconnects, but the server&#x27;s `/events` handler sends `event: connected` with `{}` (incidents.ts:31) — no replay, no event ids, no `Last-Event-ID` handling — and the client registers no `onopen`/resync (line 260 is an explicit no-op `es.onerror`). Every upsert/delete broadcast while the stream was down is therefore never applied, and `serverState` / log baselines stay at the pre-gap values. Because the watcher diffs the store against `serverState` (lines 178-187), the stale copy looks &#x27;clean&#x27;, so nothing re-fetches; the next local edit PUTs the stale blob (finding 1) and erases everything peers did during the gap. Heroku cycles dynos at least once a day and on every deploy, and laptops sleep, so every connected editor experiences this gap routinely.</p>
<p><span class="k">Failure scenario.</span> Operator A has incident X open; the dyno restarts (or A&#x27;s laptop sleeps for 60 s). During the gap operator B moves X to Recovery, assigns two Section Chiefs and adds three draw layers. A&#x27;s EventSource reconnects and receives `connected {}`; A still sees Active with the old org chart and map. A corrects the incident location field → PUT with A&#x27;s stale blob → B&#x27;s status change, assignments and draw layers are deleted server-side; B&#x27;s screen reverts on the echo. Deletes missed during the gap are equally dangerous: A keeps an incident an admin deleted, and A&#x27;s next edit re-creates it via POST (finding 4).</p>
<p><span class="k">Suggested fix.</span> On `es.onopen` (and on `visibilitychange` back to visible) refetch GET /api/incidents and run it through the same merge path as an upsert (respecting pending/inflight); or give broadcasts monotonically increasing ids, send `id:` lines, keep a short ring buffer server-side and replay from `Last-Event-ID` on reconnect (falling back to a full refetch when the id is too old).</p>
<p class="small"><span class="k">Verification.</span> Confirmed by 1 independent review (confidence: high). <span class="k">Reviewer note:</span> Minor overstatement on the Heroku angle: while a single dyno is restarting no peer can write either, so a restart only exposes the reconnect skew between clients. Laptop sleep, network blips and per-connection drops are the realistic long-gap cases.</p></div>

<div class="finding"><div class="head"><span class="sev medium">medium</span><span class="id">F-024</span><span class="t">Peer/admin delete is dropped while a local edit is pending; the resulting 404 on PUT clears the baseline and the next store change re-creates the incident via POST upsert</span></div>
<div class="loc">client/src/crisis/IncidentSync.tsx:253 &middot; correctness</div>
<p><span class="k">What happens.</span> The SSE `delete` handler ignores the event whenever a debounced write is armed for that id (`if (!id || pending.has(id)) return;`, line 253). The pending PUT then hits `UPDATE ... WHERE id=$2` on a row that no longer exists → 404 (incidents.ts:99) → the client&#x27;s catch deletes the baseline (`serverState.delete(incident.id)`, line 69). On the next store change of ANY incident, the watcher sees this incident with `known === undefined` and treats it as newly created: `pushIncident(inc, &#x27;POST&#x27;)` (lines 182-183). POST /api/incidents is `INSERT ... ON CONFLICT DO UPDATE` (incidents.ts:65-75), so the row is re-inserted with the client&#x27;s full blob and broadcast to everyone. The server-side deletion also revoked the incident&#x27;s share links (incidents.ts:255), but the resurrected blob still lists them as `active: true`, so the editor UI shows live links that are actually revoked. <div class="finding"><div class="head"><span class="sev medium">medium</span><span class="id">F-026</span><span class="t">Log-entry text typed while that entry&#x27;s own POST/PATCH is in flight is not re-diffed on settle: &#x27;Saved&#x27; is shown while the server holds stale text, and a late echo wipes the typed text</span></div>

<div class="finding"><div class="head"><span class="sev low">low</span><span class="id">F-030</span><span class="t">Checklist toggle responses are applied in arrival order: a fast check/uncheck whose responses arrive reordered leaves the editor&#x27;s checkbox opposite to the server until the next broadcast</span></div>

<div class="finding"><div class="head"><span class="sev high">high</span><span class="id">F-031</span><span class="t">Lightning query memo Map is never pruned: every distinct (minutes, lat, lon, radius) key permanently retains a serialized body of up to ~560 KB on a public, unauthenticated route</span></div>
<div class="loc">server/src/routes/lightning.ts:466 &middot; resource-leak</div>
<p><span class="k">What happens.</span> queryMemo (line 354) is a module-level Map&lt;string,{at,body}&gt;. The GET handler builds memoKey from user-controlled query params (line 370-372: `${minutes}:${qLat.toFixed(3)},${qLon.toFixed(3)},${radiusMi}` or String(minutes)) and stores the full JSON body with queryMemo.set(memoKey, ...) at line 466. A body can carry MAX_RESPONSE = 20,000 points across three arrays (~28 bytes per point once serialized, ~560 KB). The route is mounted without auth (index.ts:143). The client&#x27;s risk report legitimately generates a new key per property (client/src/riskreport/assembleWildfire.ts:185 sends lat/lon to 3 decimals with radiusMi=130 for every report target), and the unfiltered path alone admits 1,440 distinct `minutes` keys.</p>

<div class="finding"><div class="head"><span class="sev medium">medium</span><span class="id">F-035</span><span class="t">TtlCache staleOnError never re-arms the cache, so during an upstream outage every sequential request re-runs the failing fetch and waits its full timeout before returning stale data</span></div>

# Appendix C — Method

**Discovery.** Eight reviewers each examined the codebase through one lens: authentication and sessions; share links and data exposure; injection, server-side request forgery and cross-site scripting; multi-operator concurrency and sync; server resource management; Cesium entity lifecycle on the client; client state and logic; and external-feed parsing. Each was required to cite the file and line of every claim and to describe a concrete failure scenario, and was told that the prior implementation plan's audit could be used only as a lead — every claim had to be re-verified against the current code.

**Deduplication.** Findings from different reviewers that cited the same file within five lines, or whose titles shared most of their significant words, were merged; the number of independent reporters is recorded on each card.

**Verification.** Every unique finding was handed to an adversarial reviewer with instructions to refute it through three lenses — does the code actually behave as claimed, can a realistic input or state reach the failure in the deployed application, and is the behaviour a genuine defect rather than documented design — and to default to refuting when the evidence was ambiguous. Critical- and high-rated findings received a second, independent deep verification. A finding survived only if no majority of its reviews refuted it; verifiers could also correct details and calibrate severity, and those corrections are shown on the cards.

**Scope.** Static review of the repository at commit `f008edf` on `main`. No dynamic testing against a running deployment was performed; scenarios were traced through the code and its callers.
